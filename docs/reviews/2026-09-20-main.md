## Summary

The set fixes the startup splash flash by making the exit fade wait for a new `ready` prop and hold its final frame with `fill: "forwards"`, then wiring the handover through `onComplete` in `PrivateAppStartupGate`; the tests were updated to assert the absence of the mount time exit, which is the actual regression. I traced every caller and every path that can end the handover: nothing completes twice (`requestedRef` plus an idempotent provider setter), nothing new fails to complete (the readiness condition is byte for byte the one the deleted effect used), reduced motion behaves correctly, and StrictMode's double invoked effect cannot double fire because the surface mounts with `ready` false. The release shape is right — `fix(web)` earns a patch, the `docs:` and `chore(e2e)` commits earn nothing, no version is hand edited, and no deployment surface (D1 migration, Worker binding, CSP entry, service worker rule, Pages build input) is touched — and `.env.e2e` cannot reach a commit or a build artifact. The four minors below are the exit the other three call sites lost, the 4 second safeguard cutting the fade short, one unpinned reduced motion case, and the in app patch list, which AGENTS.md asks about before releasing.

## Minor

### 🟡 `ready` defaults to false, so three call sites lose the exit and `onComplete` is inert without it, `apps/web/src/components/layout/FullPageLoadingStatus.tsx:53`

**Problem**: The exit effect now returns immediately unless the caller sets `ready` (`FullPageLoadingStatus.tsx:86`), but three of the four call sites pass neither `ready` nor `onComplete`: the app wide Suspense fallback (`apps/web/src/App.tsx:153`), `RequireAuth` (`apps/web/src/auth/RouteGuards.tsx:14`) and `PublicOnly` (`apps/web/src/auth/RouteGuards.tsx:32`), and the sign in handoff (`apps/web/src/pages/AuthCallbackPage.tsx:151`). On those surfaces the splash can no longer play any exit at all; it unmounts instantly. Nothing in the props type stops a caller from passing `onComplete` without `ready` either, in which case the callback never fires and the component has no timeout of its own (the 4 second safeguard lives in the gate).

**Why it matters**: the loss of the fade on those surfaces is a polish change, not a correctness one — the old mount time fade was the bug, so nothing good is being removed — but the contract is now implicit: a caller either knows to pass the pair or silently gets neither the exit nor the callback. A future caller who copies the gate's wiring and forgets `ready` gets a splash that never hands over. The CHANGELOG's "one fade in, one hold, and one fade out" (`CHANGELOG.md:12-13`) is only true for the gate.

**Suggested fix**: make the pair explicit in the props type (`onComplete` only allowed alongside `ready`, e.g. a discriminated union) or state in the prop doc that a caller which unmounts the surface itself gets no exit; then decide, once, whether the guard and fallback call sites should fade and record it in a comment.

### 🟡 The 4 second safeguard bypasses the exit, so a slow startup loses the tail of its fade, `apps/web/src/components/layout/PrivateAppStartupGate.tsx:85`

**Problem**: `ready` (via `startupReady`, `PrivateAppStartupGate.tsx:96`) arms the 240 ms exit, and the unchanged safeguard calls `completeInitialDashboardExperience` directly at 4 seconds (`PrivateAppStartupGate.tsx:87-90`). A startup that turns ready between roughly 3.76 s and 4 s has its fade cut mid flight; one that stalls has no exit at all and the surface is removed while it is still fully opaque. This is the one path where "the splash owns the handover" does not hold, and the gate suite has no fake timer test for the safeguard at all.

**Why it matters**: the window is exactly the case this fix is about — a slow session restore or a slow dashboard request — and the symptom it produces is the abrupt reveal the set set out to remove, which will be hard to reproduce and easy to misread as a new bug.

**Suggested fix**: let the safeguard force the handover through the splash (OR a `forced` flag into the `ready` it passes, worst case 4.24 s) instead of unmounting it, or, if the abrupt cut is deliberate, say so in the comment and pin it with a fake timer test.

### 🟡 Reduced motion no longer waits for readiness, and no test pins it, `apps/web/tests/full-page-loading-status.test.tsx:302`

**Problem**: the fix moves the `ready` check above the reduced motion branch, which is a real behaviour change under `prefers-reduced-motion: reduce`: the surface used to complete on mount and now waits for the workspace. The only reduced motion test passes `ready` already true, so nothing fails if the branch order flips back to the old one — and under reduced motion there is no `animate` call to observe, so the mount time completion would return silently.

**Why it matters**: this is the branch where a regression leaves users with no splash at all rather than a visible glitch, and the suite would stay green.

**Suggested fix**: one test: with `motionState.reduceMotion = true`, render without `ready` and assert `onComplete` is not called; rerender with `ready` and assert exactly one call.

### 🟡 The in app patch list still leads with the 2.41.0 batch, and 2.41.3 will re-present it, `apps/web/src/releases/currentRelease.ts:12`

**Problem**: AGENTS.md says the in app patch list "must be updated as needed before releasing" and to update it before releasing. The set records this user visible fix in `CHANGELOG.md:9-13` but leaves `currentRelease.ts` untouched, and `ReleaseNotesExperience` gates on `currentRelease.version === __APP_VERSION__` (`apps/web/src/components/releases/ReleaseNotesExperience.tsx:27`, `:52`), so the next build shows the same six 2.41.0 notes as new with no mention of the splash. Note the precedent: `git log` shows `currentRelease.ts` has not changed since v2.41.0, so 2.41.1 and 2.41.2 — including the Google sign in fix — also shipped without an in app note, so "as needed" may be the intent here.

**Why it matters**: either users read a "what's new" note that does not describe what changed, or the omission is deliberate and undocumented for the next release. The release gate will not catch either.

**Suggested fix**: add one change to the current batch and pin it in `apps/web/tests/current-release.test.ts:27-47` (the test asserts the exact titles and copy), or state in the release commit that this patch needs no in app note.

## Nits

- ⚪ `playwright.config.ts:9-13`, the bare `catch {}` swallows every error, not just the missing file: a directory at that path throws `ERR_INVALID_ARG_TYPE` and an unreadable file throws `EACCES`, and both silently disable the authenticated half instead of failing. Node's parser also accepts a line like `E2E_EMAIL audit@example.com` (no `=`) without complaint and leaves the variable unset, so a typo in `.env.e2e` degrades to skipped tests with a green exit — the exact trap `docs/local-supabase.md:261-265` says the stub exists to close. Catch only `ENOENT`, or warn when the file exists but leaves the four keys unset. (Verified on Node 26: a missing file is `ENOENT`, a directory is `ERR_INVALID_ARG_TYPE`, and malformed lines do not throw.)
- ⚪ `playwright.config.ts:10`, `loadEnvFile` writes the whole file into `process.env`, which the two `webServer` children inherit (Vite dev on 5173 and the API's `dev:e2e`). Harmless for the four `E2E_*` keys, but a `VITE_*` key added to `.env.e2e` would reach the local dev bundle. A line in the file comment (or a key check) keeping it to `E2E_*` would prevent that.
- ⚪ `CHANGELOG.md:12-13`, "startup is one fade in, one hold, and one fade out" holds for the private startup gate only; the public route fallback and the two auth guards never fade out (see the first Minor).
- ⚪ `tmp/loading-flicker/` (gitignored, outside this diff) still holds a copy of the pre fix component, the Playwright logs, and a `.env.probe`. It cannot ship, but a stale duplicate of `FullPageLoadingStatus.tsx` will drift, and this repository has already pushed a proof artifact to main once (de3eac6). Delete it once the fix lands.

- Release shape: `fix(web)` on a user visible bug yields a patch (last tag v2.41.2, so 2.41.3), `docs:` and `chore(e2e)` are non releasing, no maintenance work is mislabelled, no product version is hand edited, and the production release workflow's inputs are untouched.
