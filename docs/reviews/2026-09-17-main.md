## Summary

The slice adds four public pages (two peso guides, two feature explainers) through the existing manifest and prerender pipeline, a content freshness guard that dates each public route from git history, and a six event signup funnel with policy copy that names it. The page pipeline work is careful: the closed `FeaturePagePath` union, the manifest derived sitemap and structured data, and the claim audit all hold up, and the 79 tests in the touched suites pass. The dangerous ground is the analytics slice. Two findings block it: every funnel event hands PostHog a payload whose system properties include the full page URL, so on authenticated pages it carries free text and account and category identifiers that both policies promise are never sent, and the funnel capture path never consults the cookie consent gate even though the cookie policy it edits says Analytics is off by default and optional technology must not load before consent. Four of the six events now fire from inside the authenticated app, which is exactly what the untouched sentence in that same policy says PostHog does not do.

## Blockers

### 🔴 Funnel events ship the private page URL, so the policy promise that they never include free text or account and category identifiers is false, `apps/web/src/analytics/funnel.ts:69`

**Problem**: `captureFunnelEvent` calls `posthog.capture(name, allowedProperties(name, properties))` with nothing to constrain the properties posthog-js adds itself. The allow list at `funnel.ts:44` only filters what this module passes. posthog-js attaches its own system properties to every capture, and its `$current_url` is the full `window.location.href`, query string and fragment included. I confirmed this against the installed SDK (posthog-js 1.418.10) with the exact init options from `PostHogAnalytics.tsx:22` and a private URL:

```
"$current_url":"https://app.zoption.site/app/transactions?search=rent%20gcash&from=2026-09-01#txn-42"
```

That payload also carried `$referrer`, `$timezone`, `$raw_user_agent`, `$pathname` and `distinct_id`. Four of the six events fire on authenticated surfaces: `app_session_started` from `PrivateAppStartupGate` on whatever `/app/*` route the user loaded, `first_import_committed` from the import surfaces, and the two assistant events. Private routes do write user data into the URL. `TransactionsPage` writes its filters there on purpose (`writeFiltersToParams`, `apps/web/src/pages/TransactionsPage.tsx:159-177`, with the comment "Filters write to the URL so a view can be bookmarked or reloaded"), and those filters include the free text `search` field plus the `account` and `category` identifiers. The existing pageview path already knew this: it builds `$current_url` by hand from origin and pathname only, dropping the query and fragment (`apps/web/src/analytics/PostHogAnalytics.tsx:71-74`). The new module does not.

Meanwhile the copy this slice adds promises the opposite. `apps/web/src/pages/legal/CookiePolicyPage.tsx:46-48`: "These steps are cookieless, carry no financial detail, and write nothing to your device: they never include an email, name, amount, category, account, or tenant identifier, free text, or a persistent identifier." `apps/web/src/pages/legal/PrivacyPolicyPage.tsx:87-89` repeats it verbatim. On a finance product that is a written promise the code does not keep.

**Concrete scenario**: a signed in user filters transactions by account and by the search text "gcash rent", then reloads or bookmarks `/app/transactions?search=gcash%20rent&account=<id>&category=<id>`. The startup gate fires `app_session_started` and PostHog receives the merchant text they typed and their account and category identifiers as `$current_url`. Nothing in the event module, the test suite, or the review checklist can see it, because `funnel.test.ts:68-69` explicitly scopes itself to the payload the module hands to `posthog.capture` and states that PostHog adds its own system properties.

**Suggested fix**: do not let posthog-js derive the URL for these events. Either configure `sanitize_properties` (or `before_send`) in `ensurePostHogInitialized` to replace `$current_url` with origin plus pathname for funnel events, the same rule the pageview path already uses, or pass an explicit sanitized `$current_url` and strip `$referrer`. Then assert it where it can be caught: add a test that runs the real posthog-js capture and inspects the whole payload, including system properties, rather than the module's arguments. If the team would rather not sanitize, the policy sentence has to be rewritten to say the page URL is sent, which for a finance product is the worse trade.

### 🔴 Funnel capture ignores the cookie consent gate and initializes PostHog on the signup page and on every authenticated page load, `apps/web/src/analytics/funnel.ts:64`

**Problem**: `captureFunnelEvent` gates only on `ensurePostHogInitialized()`, which returns true whenever `VITE_POSTHOG_KEY` is set and calls `posthog.init` on first use (`apps/web/src/analytics/PostHogAnalytics.tsx:17-42`). It never reads consent. `PostHogAnalytics` is mounted unconditionally in `apps/web/src/main.tsx:46`, and the project already has the right machinery sitting unused: `registerOptionalIntegration` in `apps/web/src/consent/consentGate.ts:77` has zero call sites in the whole web app. So a user who clicked "Reject All" still gets funnel events, now from `/signup` and from inside the authenticated app. The same cookie policy this slice edits says Analytics is "off by default" (`CookiePolicyPage.tsx:34`), that revocation "blocks future optional activity" (`CookiePolicyPage.tsx:80-81`), and that "Optional technology must not load before the corresponding consent" (`CookiePolicyPage.tsx:101`).

To be fair about what is new: the public pageview path already initialized PostHog without a consent check, and `isEligiblePublicUrl` previously kept `/signup` and `/app/*` ineligible, so on a cold load PostHog did not start there. This slice changes that. The first `signup_viewed` or `app_session_started` in a page load now starts PostHog on a surface the consent record was never consulted about.

**Concrete scenario**: a privacy conscious visitor clicks "Reject All" on the landing page, creates an account, and imports a statement. On every page load the funnel's first call initializes PostHog and sends `signup_viewed`, `signup_submitted`, `app_session_started`, `first_import_committed` and the assistant events, each carrying the URL described in the finding above. Their recorded choice said no.

**Suggested fix**: register the PostHog integration through `registerOptionalIntegration("analytics", ...)` and have `captureFunnelEvent` drop events while analytics consent is denied, or consult `getConsentGatePreferences()` before the first capture. Also decide and document whether a cookieless measurement genuinely needs consent in the target market. If it does not, the policy text ("off by default", "must not load before the corresponding consent") has to change instead, because right now the code and the policy disagree and the policy is the one users read.

## Major

### 🟠 `assistant_consent_granted` fires on click, before the grant can fail, `apps/web/src/components/assistant/AssistantConsent.tsx:88-91`

**Problem**: the button handler captures the event and then calls `onAccept()`. `onAccept` is `consentMutation.mutate()` (`apps/web/src/pages/AssistantPage.tsx:350`), an async server call that can reject; when it does, the page stays on the consent view and renders the error with `role="alert"` (`AssistantConsent.tsx:96`). The funnel has already recorded consent as granted. The spec says the event "fires when the assistant provider consent is accepted" (`docs/specs/web/0002-signup-funnel-measurement.md:104`), and the test locks the wrong timing in: `apps/web/tests/assistant-ui.test.tsx:186` asserts the event fires immediately after the click, with `accept` only checked as called. The same pattern appears at `apps/web/src/components/assistant/AssistantVoiceConversation.tsx:361`, where the voice question is recorded when a final transcript arrives, before the turn is actually sent, so a send that fails still counts as a question asked.

**Concrete scenario**: the assistant consent endpoint is briefly failing. A user clicks "Accept and continue", sees "could not enable the assistant", and never asks a question. The funnel reports one more consent granted than the server ever recorded, and because the once per page load guard marks the name as captured, a later successful acceptance in that same page load is silently dropped.

**Suggested fix**: move the capture into the success path. In `AssistantPage.tsx` add `onSuccess` to `consentMutation` (or capture inside the handler after `mutateAsync` resolves) and remove the capture from the button. Do the same for the voice question: capture where the turn is dispatched and resolves, not where the transcript lands. Update the two tests to assert the event is absent on failure.

### 🟠 The cookie policy still says PostHog does not track authenticated financial application activity, `apps/web/src/pages/legal/CookiePolicyPage.tsx:95-98`

**Problem**: section 5 reads "It receives aggregate page-use and Core Web Vitals measurements in cookieless, memory-only mode without setting analytics cookies or tracking authenticated financial application activity." Four of the six new events fire from the authenticated app by design, and the paragraph added twelve lines above names them: "a first app load, a first import into an empty workspace, assistant consent, and a first assistant question" (`CookiePolicyPage.tsx:42-49`). A first import is the single most consequential action in the product. Section 2 also still frames the measurement as being "on public pages" (`CookiePolicyPage.tsx:36-37`). The privacy policy was updated to say "that cover the signup and app surfaces" (`PrivacyPolicyPage.tsx:84`); the cookie policy was not, so two documents published on the same day, and two sections of the same document, say different things. The scope's own done criterion is "the policies name the events", so the copy is in scope for this slice.

**Concrete scenario**: a user, journalist, or auditor reads the cookie policy, believes no authenticated activity is measured, and later finds an `app_session_started` and `first_import_committed` timeline in the analytics project. The disclosure that would have covered it is contradicted by the sentence two sections below.

**Suggested fix**: rewrite the section 5 sentence to name the authenticated conversion steps and what they do and do not carry, matching the wording that was added to section 2 and to the privacy policy. Keep the distinction the code does honor: no financial workspace data, no credentials, no assistant conversations as event content.

### 🟠 The first import decision reads a cached total and never checks that the read is current, `apps/web/src/analytics/useWorkspaceTransactionTotal.ts:35`

**Problem**: the hook returns `query.data` and nothing else. It does not expose `isStale`, `isFetching` or `isError`, so both call sites decide on whatever the cache holds at the moment `onSuccess` runs (`apps/web/src/pages/ImportPage.tsx:280`, `apps/web/src/components/onboarding/SpreadsheetMigrationWizard.tsx:306`). The app's query defaults make a stale value stickier than usual: `staleTime: 60_000` and `refetchOnWindowFocus: false` (`apps/web/src/main.tsx:24-28`). I traced the cases you asked about. A second import in the same page load is safe, because the once per page load guard in `funnel.ts:65-68` blocks the second capture and the post commit invalidation does match the hook's key (`["workspace", key, "transactions", "total"]` is a prefix match for `queryKeys.allTransactions`). Two commits from the same wizard are safe for the same reason. A failed request or a still loading request is safe, because `query.data` is then undefined and no event fires. The gap is the cached case, and it fires the event when it should not.

**Concrete scenario**: a user opens `/app/import` on an empty workspace, uploads a statement, and the total is read as zero. They leave the preview open while reviewing rows. In another tab, or in the Android app, a transaction is recorded into the same workspace. The web tab still holds zero, because focus refetch is off and the data is treated as fresh. They commit the import, and `first_import_committed` fires for a workspace that already held a transaction. The metric the whole slice exists to produce is over counted, and the over count lands on exactly the users who are most active. A narrower version of the same gap: after a commit the total query is invalidated, but if its observer is already gone the refetch does not happen, so a remount inside the same page load can serve the old zero while the remount refetch is in flight.

**Suggested fix**: read the total at decision time instead of at preview time. Call `queryClient.fetchQuery` with the same key inside the commit success path (or expose `refetch` from the hook and await it before deciding), and only then compare to zero. If the read fails or has never resolved, do not fire, which keeps the spec's fail closed rule. Consider also reading `isFetchedAfterMount` so a value cached from before this page load cannot decide the event.

## Minor

### 🟡 A shared source lets a stale page date pass the freshness guard, `apps/web/src/seo/contentSources.ts:29-32` and `apps/web/tests/content-freshness.test.ts:98-100`

**Problem**: a source listed by several routes is checked once, against "the newest declared date among them". That is a deliberate tradeoff, and it is documented, but it means the guard never enforces that a _particular_ page's date matches the source that changed. All six guides share `packages/shared/src/financeGuides.ts` and `GuideDetailPage.tsx`; both feature explainers share `FeaturePage.tsx` and `featurePages.ts`.

**Concrete scenario**: in December someone corrects a figure in the salary guide. `financeGuides.ts` gets a new commit date of 2026-12-03. They bump the 50/30/20 guide's `updatedDate` to 2026-12-03, the newest declared date in the family, and the guard passes. The salary guide, whose copy actually changed and whose `updatedDate` still says 2026-09-16, keeps advertising a three month old page and its `<lastmod>` and `WebPage.dateModified` stay stale. The done criterion says "CI fails when a page's declared date no longer matches the last commit that touched its sources"; for shared sources it does not.

**Suggested fix**: give a family one declared date per source file, or split the copy per page so each route owns its own file. If neither is worth it, say so in the module comment as a known limit rather than framing the grouping as a freshness guarantee, and add a reviewer checklist line for guide edits.

### 🟡 The FAQ page's visible copy lives in a file the guard deliberately excludes, `apps/web/src/seo/contentSources.ts:50`

**Problem**: `/faq` is mapped to `FaqPage.tsx` only, and the comment at `contentSources.ts:41-43` excludes `siteMetadata.ts` because it holds the declared dates. But the page's question and answer copy is `FAQ_ITEMS_PUBLIC`, exported from that same file (`apps/web/src/seo/siteMetadata.ts:211`) and rendered by `apps/web/src/pages/faq/FaqPage.tsx:66`. The declared date lives next to the copy, so the guard can never see a copy edit there.

**Concrete scenario**: someone rewrites ten FAQ answers about fees and data retention in `siteMetadata.ts`. `FaqPage.tsx` is untouched, so the guard passes and `<lastmod>` still carries the old date, on a page whose answers just changed materially. The same shape applies to every page whose title or description in `PUBLIC_ROUTE_METADATA` is rewritten, though for those the declared date is at least in the same file.

**Suggested fix**: move `FAQ_ITEMS` into its own module and list it for `/faq`, the way the import guides and feature pages already do. That is the pattern the module comment points people at.

### 🟡 The feature explainers carry two dates that must be kept in step by hand, `apps/web/src/pages/features/featurePages.ts:39-41`

**Problem**: `FEATURE_PAGES_LAST_MODIFIED` ("2026-09-16") feeds the sitemap `lastmod` and `WebPage.dateModified`; `FEATURE_PAGES_LAST_UPDATED` ("September 16, 2026") is the human visible "Last updated" line on both pages. Nothing derives one from the other and no test compares them. The guides avoided this by rendering the ISO string directly (`GuideDetailPage.tsx:83`).

**Concrete scenario**: a future edit bumps the ISO constant and forgets the prose one. The page tells readers "September 16, 2026" while the structured data and the sitemap tell crawlers a later date, which is the same class of dishonesty the freshness guard exists to prevent, in the one place the guard cannot see.

**Suggested fix**: derive the display string from the ISO constant with one formatter, or add an assertion to `feature-pages.test.tsx` that the two agree when parsed. One line either way.

### 🟡 The freshness guard is one directional, so a date set too new always passes, `apps/web/tests/content-freshness.test.ts:102`

**Problem**: the check is `newest.declared < sourceDate`, and the only upper bound is `seo-metadata.test.ts:57-63`, "never ahead of today". So any date between the source commit and today is accepted, whether or not the content changed. This slice is itself the evidence that the lower bound has value (the first run forced PRICING, FAQ and TUTORIALS from 2026-08-30 to 2026-09-13, `siteMetadata.ts:299-313`), but nothing stops the next author from setting today's date on every route to make CI green, and nothing records why a date moved.

**Concrete scenario**: a copy cleanup touches six files at once. The author sets all six declared dates to today to clear the failures. From then on every page claims to be fresh on a day when only a comma changed, and no reviewer can tell which pages actually had material edits.

**Suggested fix**: this is hard to automate honestly, so treat it as a process note rather than a code change: require the commit message or a review line to name which page copy changed when a declared date moves, and consider a check that at least one source file in the route's list changed in the same commit as its date bump, which is cheap and catches the "bumped to go green" case.

### 🟡 Google signups never produce `signup_submitted`, so the funnel silently drops them, `apps/web/src/pages/SignupPage.tsx:32-34`

**Problem**: `signup_viewed` fires on mount for everyone, but `signup_submitted` is only captured inside `handleSubmit` (`SignupPage.tsx:67-80`). The social button path goes through `signInWithSocial` and navigates away, so a Google signup produces step one and then step three with nothing in between. `app_session_started` still fires, so the person appears at the end of the funnel while missing the middle. The spec's outcome enum has only three values and the author followed it, so this is a spec gap as much as a code gap, which is why it is a Minor and not higher. It matters because the metric the scope names is "signup to first import", and the way it will be read is a funnel chart whose second step excludes an entire signup method.

**Concrete scenario**: half of new accounts come from Google. The funnel chart shows a large drop from `signup_viewed` to `signup_submitted`, and the team concludes the email form is the problem, when in fact those users were never counted at that step.

**Suggested fix**: add an outcome for the social path, or fire a distinct step once the OAuth redirect returns (the callback page already exists), and note the limitation in the spec. Either way, decide deliberately rather than by omission.

### 🟡 The landing receipt panel claims more than the explainer it now links to, `apps/web/src/pages/LandingPage.tsx:586-591`

**Problem**: the panel says the vision engine "detects the merchant name, date, subtotal, sales tax, and line items automatically", and this slice adds a link from that panel to `/features/receipt-scanning` (`LandingPage.tsx:608-613`). The explainer says the draft holds "merchant, date, total, and a likely category" (`featurePages.ts:48`, `featurePages.ts:63`), and the web receipt draft type carries merchant, amount, date and category with no line items at all (`apps/web/src/components/receipts/ReceiptEntry.tsx:20`, `apps/web/src/components/receipts/ReceiptEntry.tsx:160-170`). The spec explicitly defers the landing page's own claim review to follow up (`0001-search-demand-pages.md:152`), so the pre existing over claim is not this slice's to fix, but the new link now routes readers from it straight into copy that contradicts it.

**Concrete scenario**: a reader compares the two pages a click apart and finds the marketing panel promising sales tax and line items that the explainer and the product do not deliver. On a finance site the accuracy bar is the product.

**Suggested fix**: either narrow the landing panel to merchant, date, total and category, or ship line item extraction before the claim stands. If it stays, keep the follow up open and make sure the explainer is the page the search result lands on.

## Strengths

- The closed event union plus the capture time allow list is the right shape for this problem, and the test that passes `email`, `amount_minor` and `tenant_id` and asserts they are stripped is exactly the test to have (`apps/web/tests/funnel.test.ts:78-89`). The failure mode that remains is outside the module, which is a much better place to be than inside it.
- `useWorkspaceTransactionTotal` reuses the transactions list request instead of adding a key to the commit response, and the reasoning in the spec for that is sound: the response is decoded with a strict schema, so a new key breaks installed Android builds. I verified the value it reads is the right one: `total` is a `COUNT(*)` over every logical row for the tenant with no default date window (`apps/api/src/db/transactions.ts:320-346`), so "total is zero" really does mean the ledger is empty, and the read is fail closed when it does not resolve.
- `fetch-depth: 0` was added to the one job that runs `pnpm test`, with a comment saying why, and the date handling is actually correct: `--date=format-local:%Y-%m-%d` with `TZ=UTC` gives the UTC calendar day of the author date, which is the same clock `seo-metadata.test.ts:58` uses for "never ahead of today", so the two guards cannot disagree. Most versions of this guard get the timezone wrong.
- The manifest work holds together: `FeaturePagePath` is a closed union built from the data module, so adding a page to `FEATURE_PAGES` fails typecheck until it is registered in `PUBLIC_ROUTE_METADATA` and `PUBLIC_ROUTE_ELEMENTS`, and prerender and the sitemap follow from `PUBLIC_ROUTE_PATHS` with no second list to keep in step (`apps/web/src/seo/siteMetadata.ts:43-65`, `apps/web/scripts/prerender.mjs:215-220`).
- The guide copy respects the claim boundary from AC-3, including the one case the spec called out by name: the salary guide says "On the web app a file can be CSV, XLSX, or XLS, and the Android app also reads PDF statements" rather than claiming PDF import for the web.

## Test coverage

Test signal: **configured** (vitest, `apps/web/package.json` has `test: vitest run`, and the repo runs widespread suites; there is no `test-preferences.json`). I ran the ten touched suites: 79 tests, all passing, including the content freshness guard against the real git history at HEAD.

Covered and genuinely useful: the closed union, the property allow list, the once per page load guard, the silent no op with no key and on a throwing capture, each wired surface at least once, and both first import branches on the import page and the wizard.

Not covered, and these are the gaps that matter: nothing exercises the real posthog-js payload, so the system properties that carry the private URL are invisible to the suite, and the module test's own comment says so; nothing asserts any relationship between consent state and capturing; the assistant consent test asserts the wrong moment and would fail if the capture moved to the success path; and the freshness guard has no test proving that a per page stale date still fails, because with shared sources it does not.
